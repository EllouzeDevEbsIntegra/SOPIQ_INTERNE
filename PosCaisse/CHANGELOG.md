# Changelog

## 1.0.0 — 2026-09-04

- Structure initiale du projet (backend Spring Boot 3.5 / Java 21, frontend Vue 3 / Vite, PostgreSQL 16, Flyway).
- Backend core : schéma V1, entités, sécurité JWT + PIN, rôles/permissions, catalogue, sessions de caisse, ventes (checkout idempotent, attente/reprise, annulation, remboursement), journal, mouvements, clôtures, impression (rendu 58/80 mm, routage, jobs), rapports, audit, jeu de démonstration.
- Frontend POS tactile : connexion PIN, ouverture de caisse, écran POS (favoris, catégories, tuiles, recherche, panier), options/menus, paiement mixte + rendu, tickets + impression, commandes en attente, mouvements de caisse, clôture, historique des tickets.
- Back-office : dashboard, tickets, journal, sessions, clôture journalière, rapports + CSV, produits/menus, catégories, options, disposition POS/favoris, clients, utilisateurs, rôles, entreprise/PDV/caisses, moyens de paiement, tickets & impression, paramètres, audit.
- Corrections après tests : ventes espèces nettes en clôture, erreurs 400 sur paramètres invalides, style de tuile menu, pavé numérique (valeur initiale remplacée), débordement du panier en 768 px, composition de menu (sous-options seulement si obligatoires), aperçu ticket (transaction).
- Tests unitaires + scénario d'intégration, scripts Windows/Linux, documentation.

- Correction des lanceurs Windows : les `.bat` étaient enregistrés avec des fins de ligne Unix (LF). `cmd.exe` mal-interprète ce format dès qu'un script contient des blocs entre parenthèses ou des étiquettes — `RESTART_POS.bat` s'ouvrait puis se fermait sans rien lancer. Un `.gitattributes` impose désormais CRLF aux `.bat`/`.ps1`, et la logique a été déplacée dans `restart.ps1` et `init-db.ps1` (PowerShell 5.1, sans dépendance) : les `.bat` ne sont plus que des lanceurs d'une ligne, `START_POS.bat` appelant `restart.ps1 -Mode start`.
- Nettoyage définitif du catalogue : `POST /api/catalog/purge` (permission `PRODUCTS_MANAGE`), scripts `CLEAN_CATALOG.bat` / `clean-catalog.sh`. Sans option, seuls les articles inactifs jamais vendus, les catégories vides et les groupes d'options orphelins disparaissent — l'historique reste intact et l'utilisateur est averti de ce qui a été conservé et pourquoi. Avec `resetSales`, toutes les données transactionnelles sont effacées d'abord (ce qui libère les articles déjà vendus), la numérotation des tickets repart à 1, et l'opération est refusée tant qu'une caisse est ouverte.

Le paquet embarque l'application, l'interface **scellée dans le JAR** (profil Maven `bundle`), le moteur Java et le serveur PostgreSQL. Le PC du client n'a besoin ni de Java, ni de PostgreSQL, ni de Node, ni de droits administrateur, ni de connexion : rien n'est installé dans Windows, aucun service n'est enregistré, copier le dossier déplace l'installation. L'installation crée un serveur PostgreSQL privé au mot de passe tiré au hasard, à l'écoute de `127.0.0.1` seulement, sur le port 5433 pour cohabiter avec un PostgreSQL déjà présent. Lanceurs `DEMARRER` / `ARRETER` / `SAUVEGARDER` / `RESTAURER` / `ETAT`, réglages dans un fichier texte, `LISEZ-MOI.txt` pour le client et `INSTALLATION-AUTONOME.md` pour l'intégrateur. Une mise à jour ne remplace que `poscaisse.jar` : les données vivent à part, dans `donnees/`.
- Correction : `build-bundle.ps1` refusait de démarrer sous Windows PowerShell 5.1 avec une erreur de syntaxe ligne 106, alors que la faute était ligne 4. Sans marque d'ordre des octets, PowerShell 5.1 lit un fichier comme de l'ANSI : le tiret cadratin `—` y devient `â€"`, dont le dernier caractère est un guillemet fermant pris pour un délimiteur de chaîne — tout le script suivant était avalé. Les six scripts `.ps1` du dépôt sont désormais en ASCII pur **et** portent une marque d'ordre des octets ; `packaging/verifier-scripts.sh` le contrôle et la fabrication du paquet l'exécute d'abord. PowerShell 7, qui lit l'UTF-8 par défaut, ne montrait pas le problème — d'où sa découverte seulement à l'exécution.
- Correction : `INSTALLER.bat` annonçait « la creation du serveur de base a echoue » sans jamais dire pourquoi — la sortie de `initdb` était filtrée sur les lignes contenant « error », et le message réel n'y figurait pas. Elle est désormais conservée en entier dans `journaux/initdb.log` et affichée telle quelle en cas d'échec. Deux causes fréquentes sont en plus détectées **avant** de commencer : une fenêtre ouverte en tant qu'administrateur (PostgreSQL refuse de fonctionner ainsi) et l'absence de la bibliothèque Microsoft VC++ (`initdb --version` sert de test). Le paquet embarque désormais `vc_redist.x64.exe`. Le contrôle des scripts refuse aussi la double marque d'ordre des octets, qui casse le langage aussi sûrement que son absence.
- Correction : la fabrication du paquet échouait sous Windows sur « Unable to rename `poscaisse-backend.jar` to `.jar.original` » — un message qui ne dit pas d'où vient le blocage. Sous Windows un fichier ouvert ne peut pas être renommé : une caisse encore en service, ou un antivirus en train d'inspecter le JAR à peine écrit, suffit. Le script ferme désormais les caisses en cours avant de compiler, ajoute `clean` (un JAR laissé par une compilation précédente est le premier candidat au blocage), retente trois fois avec une pause — les verrous d'antivirus sont transitoires — et, s'il renonce, nomme les trois causes possibles au lieu de renvoyer au message de Maven.
- Correction : la fabrication du paquet restait bloquée sous Windows, même après trois tentatives, sur « le fichier est utilisé par un autre processus ». Le coupable était la caisse elle-même : `START_POS.bat` la lance par `java -jar target\poscaisse-backend.jar` dans une fenêtre **réduite**, facile à oublier, et Windows interdit de supprimer ou renommer un fichier ouvert. Plutôt que de lutter contre le verrou, le JAR de chaque fabrication porte désormais un nom horodaté que personne ne peut retenir (`finalName` devenu paramétrable dans le `pom.xml`, valeur par défaut inchangée pour les autres scripts) ; `clean` disparaît, seul le dossier de l'interface est vidé, et le JAR temporaire est supprimé après copie. Vérifié en tenant délibérément l'ancien JAR ouvert pendant toute la fabrication.
- Correction : la fermeture des caisses avant compilation était définie mais **jamais appelée** — mon insertion cherchait `l'application` là où le script écrit `l''application`, échouait en silence, et je n'avais vérifié que la syntaxe du fichier, pas la présence de l'appel.
- Installation autonome : le diagnostic « les programmes PostgreSQL ne demarrent pas » affichait un message **vide**. C'est la signature même d'une bibliothèque manquante — Windows refuse de charger le programme avant qu'il n'écrive quoi que ce soit — mais un message vide ne l'apprend à personne. Le code de retour est désormais toujours indiqué, avec la mention explicite « aucun message : Windows n'a pas pu charger le programme ». - Transfert des données vers un poste autonome. Le paquet s'installe avec un jeu de démonstration ; `EXPORTER_DONNEES.bat` produit sur le poste de développement un fichier reprenant la carte, l'entreprise, les utilisateurs, les réglages, les clients, les livreurs et les remarques de cuisine, que `RESTAURER.bat` installe sur le poste du client. Une coupure tombant au milieu du gras le referme et le rouvre sur la ligne suivante — un ticket à moitié gras se remarque plus qu'un ticket sans gras. Vérifié sur un ticket réel en 42 et en 32 colonnes : la colonne des montants reste alignée sur celle des lignes sans variante, et aucun marqueur ne ressort à l'écran ni à l'impression.
- **Numérotation des tickets : la remise à zéro devient un réglage, au lieu d'être devinée du format.** Jusqu'ici le compteur repartait à 1 dès que le préfixe imprimé changeait : imprimer l'année remettait donc à zéro chaque 1er janvier, qu'on le veuille ou non, et on ne pouvait pas repartir à 1 chaque jour sans écrire la date sur le ticket. Nouvel écran back-office « Numérotation des tickets » (`/admin/ticket-numbering`, permission `SETTINGS_MANAGE`) : remise à zéro **continue, journalière, mensuelle ou annuelle**, compteur séparé **par point de vente** et/ou **par caisse**, format imprimé avec insertion des jetons et formats courants, et l'exemple du prochain numéro calculé par le serveur à chaque frappe — c'est le calcul de la vente, pas une imitation. Réglages `ticket.resetPeriod`, `ticket.perPos`, `ticket.perRegister` (migration V10, déduits du format déjà en place sur chaque base : le comportement d'hier est reconduit tel quel). Un réglage dont la portée ne se lit pas sur le ticket est **refusé à l'enregistrement** et dit pourquoi, avec un bouton qui complète le format — sinon deux portées imprimeraient le même numéro et la vente serait rejetée devant le client. Les compteurs sont listés et le prochain numéro se pose à la main (`PUT /api/ticket-numbering/counter`), un numéro déjà imprimé étant refusé. Un compteur nouvellement créé démarre au-dessus du plus grand numéro déjà imprimé sous la même forme, jamais à 1 : changer de portée en cours d'année ne réémet donc aucun numéro.
- **Numérotation des tickets : ce qui s'imprime se règle à part de ce qui est enregistré.** Une référence utile à la comptabilité est longue — date, point de vente, caisse, compteur — mais le client n'a pas à la lire pour retrouver sa commande. Nouveau réglage `ticket.displayPattern`, dans le même écran : vide, le ticket montre sa référence entière comme avant ; sinon un format plus court tiré du **même** compteur (`{SEQ:4}` → `0001`, `{REG}-{SEQ:3}` → `C01-001`). L'aperçu montre les deux faces, le numéro affiché en grand et la référence en dessous. L'affichage retenu est **enregistré sur la vente** (`sale_order.ticket_display`, migration V11, rempli pour les ventes existantes avec leur référence) plutôt que recalculé : une réimpression six mois plus tard rend le ticket que le client a gardé, même si le format a changé entre-temps. Le ticket imprimé, l'écran de vente, l'historique et le détail d'un ticket montrent l'affichage ; la recherche par numéro porte sur les deux faces, puisque le caissier lit ce qui est sur le papier. Un affichage sans `{SEQ}` est refusé : tous les tickets porteraient la même mention.
- Ticket : le **« N° » imprimé d'office** devant le numéro est retiré. Depuis que l'exploitant choisit ce qui s'affiche, ce préfixe faisait doublon dès qu'il en mettait un lui-même — le papier sortait « N° N° 0001 ». Le ticket porte désormais **exactement** ce que le format d'affichage demande, mot pour mot : `{SEQ:4}` donne `0001`, `N° {SEQ:3}` donne `N° 001`, `Ticket {SEQ:4}` donne `Ticket 0001`. Le libellé appartient au réglage, plus au code. Vaut pour le ticket client comme pour le ticket cuisine.
- **Assistant de commande** (écran de vente, bouton au pied du rail des rubriques). Le client annonce sa commande d'un trait — « 4 mlewi, 2 pâte céréale omlette thon moz 3arbi dont un sans harissa, l'autre sans mayonnaise et frites à part… » — et le caissier doit la tenir en tête pendant qu'il cherche des articles dont les noms diffèrent d'un mot. L'assistant traduit : on touche les **ingrédients** que le client a dits (les 76 sandwichs de la carte les portent), trois pastilles ne laissent qu'un article sur 108. L'article touché entre aussitôt dans la commande et ouvre sa fiche : **une répartition par pâte** (1 céréale, 1 normale, 2 chia se disent en trois touches, chaque version avec son prix), puis les suppléments et les remarques cuisine du moment — un lot déplié à la fois, sans changer d'écran, la commande se mettant à jour à chaque touche. Poser une remarque sur un lot de plusieurs pose **une seule question**, la même partout : « pour combien de ces 2 ? », et le lot se scinde. Un **total annoncé** facultatif sert de contrôle (il compte les articles à pâte, c'est-à-dire les sandwichs) et retient la validation tant qu'il ne tombe pas juste ; « Relire au client » rend la commande en une phrase à dire à voix haute. À la fin, les lots deviennent des lignes de panier ordinaires — l'encaissement ne change pas. Un article à composer (menu, groupe d'options obligatoire) est renvoyé à sa fiche habituelle plutôt que d'être approximé. Aucun changement au serveur : tout vient déjà de `/api/pos/catalog`.
- Assistant de commande : le **récapitulatif** est de nouveau obligatoire avant de verser au panier — il avait disparu à l'intégration, où le bouton final écrivait directement dans le panier. « Vérifier et ajouter » ouvre désormais un tableau ligne à ligne (quantité, article, version, suppléments, remarques, prix), le compte de sandwichs face au total annoncé, le total, et la phrase à relire au client. C'est le seul moment où l'on relit avant que la commande parte en cuisine ; le sauter faisait perdre à l'assistant l'essentiel de ce qu'il apporte.
- Clôture de caisse : bouton **État de caisse** (le récapitulatif de la session rendu comme un ticket, aperçu puis impression — avant la clôture pour compter, après pour garder la pièce, avec le compte réel et l'écart), et **bénéfice estimé** d'après un nouveau réglage back-office « Marge bénéficiaire (%) ». Le bénéfice s'applique au chiffre d'affaires, pas au tiroir : une vente par carte, par chèque ou à crédit y compte même si l'argent n'est pas là, un ticket annulé ou remboursé n'y compte pas, et une sortie de caisse ne l'entame pas. À 0 — la valeur livrée — ni l'écran ni le papier n'en parlent.
- Clôture de caisse : si aucune somme comptée n'est saisie, la clôture reprend les espèces théoriques et l'écart est nul. Le caissier qui n'a pas recompté son tiroir ne veut pas déclarer zéro dinar — il veut dire « c'est bon » ; saisir zéro enregistrait pourtant un manquant égal à tout le fond de caisse, et le bouton restait éteint sans dire pourquoi. La confirmation l'annonce en toutes lettres, pour que ce ne soit jamais un choix fait à la place du caissier.
- **Stock par variante — les pâtes du jour.** Ce qui s'épuise dans un fast-food à mlewi n'est pas un article mais une pâte : la même pâte normale sert quarante sandwichs. Le compteur se pose donc sur la valeur de variante. Dans **Back-office → Variantes**, chaque version se règle en trois positions : non suivie, compteur propre (avec le pas de décrémentation), ou branchée sur une autre — « Double Normale » n'a pas de compteur, elle consomme deux pâtes normales. En caisse, un bouton **Stock** (avant « Attente ») montre ce qu'il reste de chaque pâte, laisse saisir les réceptions et déclarer les pertes avec leur motif. Une version épuisée est grisée dans l'écran de composition, et la vente est refusée côté serveur, verrou posé sur le compteur : deux caisses ne peuvent pas vendre la même dernière pâte. Le stock appartient au point de vente (pas à la caisse), une annulation rend la pâte, un remboursement non, et tout repart à zéro à la clôture journalière — la pâte ne se garde pas d'un jour à l'autre.
- Stock : le contrôle passe du moment d'encaisser au moment d'**ajouter au panier**. Un caissier qui compose toute une commande pour s'entendre dire à la caisse qu'il manque une pâte a perdu son temps devant le client. Le refus est prononcé dans le panier — le passage obligé de tout ce qui se vend —, donc il vaut pour l'appui sur la tuile, la fenêtre d'options, le + du panier et l'assistant, sans qu'aucune porte ne puisse l'oublier. La fenêtre d'options grise en plus les versions que le reste du panier a déjà prises, et la ligne en cours de modification rend d'abord sa propre pâte. Une ligne qui n'a qu'une variante affiche désormais le bouton « Options » : sans lui, changer la pâte depuis le panier obligeait à retirer la ligne et à la refaire.
- Variantes : « tire sur une autre version » ne tenait pas — l'état était déduit de la version choisie, si bien qu'en le sélectionnant le réglage retombait aussitôt sur « non suivi » et la liste des versions n'apparaissait jamais. L'état est maintenant porté par le réglage, la liste propose **toutes** les autres versions de l'axe (en désigner une lui donne son compteur, plutôt que d'imposer un ordre de gestes), et la phrase sous le réglage dit ce qui se passera : « une vente retire 2 sur Normale ».
- Stock, fenêtre de composition : le contrôle porte sur la version **sélectionnée**, et rien ne change tout seul. Le grisage « épuisé » ne dépend plus de la quantité demandée — il ne marque que les pâtes dont il ne reste pas de quoi servir un article ; auparavant, monter le compteur éteignait la version choisie, qui semblait s'être désélectionnée et faisait partir le regard sur une autre. La quantité, elle, est bornée par la pâte choisie : le « + » se bloque à son maximum, une phrase dit ce qu'il reste et combien d'articles c'est, et « Ajouter » est refusé tant que la quantité dépasse — au caissier de descendre la quantité ou de changer de pâte, jamais au logiciel de servir autre chose que ce qui a été demandé.
- **Mise en service : partir de la base d'essai, nettoyée.** `NETTOYER_VENTES.bat` efface d'une base ce qu'elle a produit — tickets, lignes, paiements, remboursements, mouvements, journal, clôtures, sessions, règlements de compte (donc les soldes clients), compteurs de tickets, stock des pâtes, audit — et ne touche à rien de ce qui a été paramétré : entreprise, caisses, carte, options, ingrédients, variantes et leurs prix, remarques cuisine, moyens de paiement, imprimantes, utilisateurs, clients, réglages. Une sauvegarde de sécurité est prise avant, et le nettoyage tient dans une transaction : en cas d'erreur, la base reste telle qu'elle était. Le script affiche ce qu'il a effacé et ce qu'il a gardé, ligne par ligne.
- L'export de mise en service (`EXPORTER_DONNEES.bat`, réponse N) laissait passer les compteurs de stock des pâtes : le client aurait démarré avec les pâtes d'un essai. Le paramétrage des variantes, lui, part toujours. Même correction dans la remise à zéro des ventes du back-office.
- Le harnais de tests du frontend ne savait pas résoudre un import de dossier (`../api` → `../api/index.js`) là où Vite le fait : un import parfaitement valide faisait échouer la fabrication du paquet. Le panier, lui, ne va plus chercher le catalogue tout seul — la caisse le lui donne avec le stock, ce qui lui évite de traîner l'appel réseau jusque dans le moindre test.
- Maintenance : `copier-prix-version.sql` recopie le prix d'une version de variante sur une autre, article par article. Le cas : une version ajoutée à un axe déjà tarifé — « Chapati » qui rejoint les pâtes — arrive à 0 sur des dizaines d'articles, et à 0 la caisse la montre grisée, donc invendable. Le script donne à la version cible le prix que chaque article donne déjà à la version source, **sans jamais écraser un prix saisi** : seules les cases vides ou à 0 sont remplies, il est donc rejouable, et il liste à la fin les articles restés à 0 (ceux dont la source elle-même n'est pas tarifée).
- Le paquet autonome reçoit `APPLIQUER_SQL.bat` : appliquer un fichier `.sql` sur la base d'un poste installé, avec le PostgreSQL embarqué (port et mot de passe propres au poste, psql absent du PATH) et une sauvegarde prise avant, systématiquement.
