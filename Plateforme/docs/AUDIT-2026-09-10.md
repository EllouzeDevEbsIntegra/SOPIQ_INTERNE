# Audit de PosCaisse SaaS — 10 septembre 2026

## Décision

La version auditée est sensiblement plus sûre et plus mesurable qu'au départ. Dix-sept
corrections ou contrats de contrôle ont été conservés, chacun dans un commit distinct.
Les suites éditeur, interface et déploiement passent deux fois de suite. La suite caisse
contient volontairement **un échec visible et non ignoré** : la requête sans contexte
client réussit encore. La cible « une application, N bases » décrite dans
`ARCHITECTURE-SAAS.md` n'est donc pas prête.

Deux risques empêchent de considérer l'ensemble prêt pour une exposition SaaS mutualisée :

1. le contexte client obligatoire n'est pas implémenté ;
2. une installation neuve de la caisse crée encore `admin / admin123`, PIN `9999`, même
   lorsque les données de démonstration sont désactivées.

Le modèle actuel, un processus et une base par client, reste exploitable à condition de
changer ce secret à l'installation et de conserver l'isolation réseau et PostgreSQL déjà
en place. Aucun paiement en ligne n'a été introduit.

## Périmètre et méthode

L'audit a porté uniquement sur `Plateforme/backend`, `Plateforme/frontend`,
`Plateforme/plateforme`, `Plateforme/deploiement` et l'emballage autonome associé.
Le dossier voisin `PosCaisse/`, qui contient la version livrée, n'a pas été modifié. Aucun
appel n'a été fait vers `135.125.100.21` ou `*.pos.ebs-integra.com`.

La ligne de base a été établie avant toute correction. Docker n'étant pas disponible, les
essais d'intégration ont utilisé un PostgreSQL **17.6 local** sur `127.0.0.1:55439`, dans
une arborescence temporaire dédiée. Cela valide PostgreSQL local, mais pas exactement la
version 16 demandée.

| Suite avant correction | Résultat |
|---|---:|
| Caisse Spring Boot | 103 réussis, 0 échec, 0 erreur, 0 ignoré |
| Back-office éditeur | 26 réussis, 0 échec, 0 erreur, 0 ignoré |
| Interface Vue | installation reproductible, compilation réussie, 21 contrôles réussis |

La campagne a ensuite suivi le même cycle pour chaque défaut : écrire le contrôle, observer
son échec, corriger, puis rejouer le contrôle. Les journaux bruts sont conservés hors dépôt
dans `D:\Temp\poscaisse-audit-20260910`.

## Défauts classés par coût

### 1. Absence de frontière multi-client dans l'application — critique, ouvert

**Reproduction.** Démarrer la caisse sans contexte client puis appeler
`productRepo.count()`. La requête part sur la source de données par défaut au lieu d'être
refusée.

**Échec gardé dans la suite normale.** `TenantContextTest` échoue avec :

```text
Expecting code to raise a throwable.
```

**État.** Le contrôle avait d'abord été ajouté comme contrat isolé. Le commit `7973f33`
l'a renommé et a supprimé le profil Maven qui le séparait : aucun profil, filtre ou
quarantaine ne peut maintenant le cacher. Les deux exécutions finales donnent 122 tests,
1 échec, 0 erreur, 0 ignoré.

**Correction nécessaire.** Porter l'identifiant client dans le jeton, l'installer dans un
contexte borné à la requête, résoudre la source de données avant toute transaction et
lever une exception si le contexte manque. Il faut aussi borner et purger le cache des
sources, adapter les tâches asynchrones et migrations, puis prouver l'isolation avec au
moins deux bases et deux identités. C'est un chantier d'architecture substantiel ; une
estimation crédible nécessite d'abord un prototype et l'inventaire des chemins qui ouvrent
une transaction.

**Garde.** `backend/src/test/java/com/poscaisse/it/TenantContextTest.java`.

### 2. Secret initial connu sur chaque caisse — critique, ouvert

**Reproduction.** Créer une base vide avec les données de démonstration désactivées. Le
socle crée tout de même l'utilisateur `admin`, le mot de passe `admin123` et le PIN `9999`.
Les lanceurs autonomes affichent encore ces identifiants.

**Coût.** Une caisse accessible avant rotation du secret peut être administrée avec une
valeur publiée dans le code et la documentation d'installation.

**Correction proposée.** Exiger un secret initial unique comme pour le back-office
éditeur, ou générer un secret à usage unique et imposer son remplacement au premier accès.
Le provisionnement doit transmettre ce secret par un canal distinct des journaux et des
arguments de processus. Ajouter un test d'amorçage sans secret et un test de rotation.

**Pourquoi il reste ouvert.** La correction modifie le contrat d'installation et la remise
du premier accès au technicien. Elle ne pouvait pas être imposée sans concevoir ce flux.

### 3. Révocation tardive des accès éditeur — critique, corrigé

**Reproduction avant correction.** Se connecter, désactiver ou supprimer le compte, puis
réutiliser son JWT. Le filtre faisait confiance aux droits et à l'état contenus dans le
jeton jusqu'à expiration. Un changement de rôle restait lui aussi sans effet immédiat.

**Correction.** Le filtre recharge l'utilisateur courant à chaque requête et refuse le
compte absent ou inactif. Les droits courants remplacent ceux du jeton. La durée éditeur
par défaut est désormais cohérente avec sa configuration, soit 120 minutes ; la caisse
garde son cycle de travail de 720 minutes.

**Garde.** Treize scénarios dans `RevocationEditeurIntegrationTest`, dont suppression,
désactivation, retrait de rôle et jeton signé par un autre émetteur. Commit `177acb8`.

### 4. Secret administrateur éditeur en dur et journalisé — critique, corrigé

**Reproduction avant correction.** Démarrer une base éditeur vide sans configuration : le
compte initial recevait `plateforme123` et la valeur apparaissait dans le journal.

**Correction.** Une base neuve exige `PLATEFORME_ADMIN_PASSWORD`, d'au moins 12 caractères.
La valeur n'est jamais écrite dans les journaux. Une base déjà amorcée redémarre sans
redemander le secret.

**Garde.** Trois scénarios dans `AmorcageSecuriteTest`. Commit `bd290a5`.

### 5. Secrets PostgreSQL visibles dans les lignes de processus — élevé, corrigé

**Reproduction avant correction.** Inspecter les lanceurs shell et PowerShell : ils
construisaient un argument Java `--spring.datasource.password=...`. Le contrôle échouait
sur :

```text
AssertionError: '--spring.datasource.password=' unexpectedly found
```

Le provisionnement éditeur transmettait lui aussi le secret dans les arguments d'une
commande enfant.

**Correction.** Les lanceurs passent le secret par environnement ou le demandent de façon
interactive. Le provisionnement utilise l'environnement du processus enfant. Le mot de
passe des rôles PostgreSQL n'est pas placé dans une option `psql -c`.

**Garde.** `SecretsProcessusTest`, pour les deux lanceurs et `preparer-demos.sh`. Commit
`9893555`.

### 6. Adresse falsifiable dans le ralentisseur de connexion — élevé, corrigé

**Reproduction avant correction.** Envoyer plusieurs valeurs `X-Forwarded-For` ou appeler
directement l'application avec cet en-tête. La première valeur, contrôlée par l'appelant,
pouvait changer la clé du compteur.

**Correction.** L'en-tête n'est accepté que si le pair direct est la boucle locale, donc le
proxy local attendu. L'adresse retenue est la dernière ajoutée par ce proxy. Un accès
direct utilise `remoteAddr`. La même règle couvre la caisse et l'éditeur.

**Gardes.** Trois scénarios dans `AdresseAuthentificationTest`, deux dans
`AdresseAuthentificationEditeurTest`. Commits `c272662` et `8567da5`.

### 7. Marge et réglages privés lisibles par un caissier — élevé, corrigé

**Reproduction avant correction.** Lire le catalogue de vente ou modifier la disponibilité
d'un article avec un caissier : les réponses contenaient le prix d'achat. Les réglages
privés étaient également accessibles sans la permission de gestion.

**Correction.** Les DTO de caisse omettent le prix d'achat et ne publient qu'une liste
explicite de réglages utiles à la vente. Les routes de réglages sensibles exigent la
permission de gestion.

**Garde.** Trois scénarios HTTP dans `AuditConfidentialiteIntegrationTest`. Commit
`f294667`.

### 8. Écriture dans la session de caisse d'un collègue — élevé, corrigé

**Reproduction avant correction.** Un caissier authentifié pouvait fournir l'identifiant de
la session ouverte par un collègue pour y enregistrer une vente ou une sortie de caisse.
Les deux nouveaux scénarios échouaient avant correction.

**Correction.** Chaque écriture vérifie le propriétaire de la session ; seul un utilisateur
autorisé à gérer les sessions peut agir sur celle d'un autre.

**Garde.** Les deux scénarios de `IsolationSessionEcritureTest`. Commit `248df1d`.

### 9. Entrées de provisionnement injectables — élevé, corrigé

**Reproduction avant correction.** Fournir un sous-domaine avec `../` ou une nouvelle
ligne, une base multiligne, un profil `.*`, une enseigne terminée par `\`, ou un port
contenant une commande. La première série comptait 6 échecs sur 10 tests.

**Correction.** Les sous-domaines, bases, profils, enseignes et ports sont validés avant
toute écriture de fichier ou commande privilégiée. Le préfixe `demo-` reste réservé et les
ports sont bornés.

**Garde.** Dix scénarios d'entrée dans `ValidationOuvertureTest`. Commit `2319e96`.

### 10. Remises en dinars hors plafond — élevé, corrigé

**Reproduction avant correction.** Une remise négative ou une remise exprimée en montant
pouvait contourner la limite personnelle exprimée en pourcentage. Sans plafond personnel,
la remise en montant ne demandait pas toujours le droit manager. Six scénarios de bord
échouaient avant la correction.

**Correction.** Le montant est converti en taux effectif et soumis au même plafond que le
pourcentage. Les valeurs négatives et quantités nulles ou égales à zéro sont refusées.

**Garde.** Neuf scénarios dans `RemisesAutoriseesTest`. Commit `34b2aaf`.

### 11. Encaissement déclenché derrière une fenêtre modale — élevé, corrigé

**Reproduction avant correction.** Ouvrir le choix du client au-dessus du paiement et
presser Entrée. Le test attendait zéro encaissement mais en observait un :

```text
expected checkout calls: 0
actual checkout calls: 1
```

**Correction.** Les fenêtres modales arrêtent l'événement clavier imbriqué, capturent le
focus, le restaurent à la fermeture, gèrent Échap et annoncent correctement leur rôle.
Les tuiles produit sont activables au clavier.

**Garde.** Six parcours dans `payment-keyboard.browser.mjs`. Commit `c4f3938`.

### 12. Liste de 200 clients en N+1 — moyen à élevé, corrigé

**Reproduction avant correction.** Charger 200 clients, chacun avec abonnement, facture et
règlement, puis appeler la liste douze fois en comptant les requêtes Hibernate.

| État | Médiane | p95 | Maximum de requêtes |
|---|---:|---:|---:|
| Avant | 651 ms | 2 224 ms | 601 |
| Après, exécution finale 1 | 41 ms | 326 ms | 13 |
| Après, exécution finale 2 | 58 ms | 254 ms | 13 |

**Correction.** La liste charge les relations nécessaires en nombre borné et construit les
DTO sans requête par client.

**Garde.** `ClientsPerformanceIntegrationTest` impose au plus 15 requêtes. Commit
`9620468`.

### 13. En-têtes web incomplets — moyen, corrigé

**Reproduction avant correction.** Le contrôle statique des deux configurations nginx ne
trouvait pas les quatre en-têtes requis.

**Correction.** La caisse et l'éditeur publient `Strict-Transport-Security`,
`X-Frame-Options`, `X-Content-Type-Options` et `Content-Security-Policy`.

**Garde.** `EntetesNginxTest`. Commit `82d4b9f`.

### 14. Socle métier pollué par la restauration — moyen, corrigé

**Reproduction avant correction.** Amorcer une supérette sans démonstration. Le contrôle
attendait seulement la destination client mais recevait :

```text
actual ["CLIENT", "CUISINE", "PIZZA", "BOISSONS", "PASSE"]
expected ["CLIENT"]
```

Le moyen de paiement « ticket restaurant » était lui aussi ajouté à tous les métiers.

**Correction.** Les destinations de préparation et le titre restaurant sont conditionnés
au profil. Une boutique reçoit seulement le socle commercial qui lui appartient.

**Garde.** `AmorcageZeroTest` et les contrôles de profils existants. Commit `03a2f02`.

### 15. Cibles tactiles trop petites — moyen, corrigé

**Reproduction avant correction.** Ouvrir les deux catalogues réels en 1024×768. Le premier
échec mesurait le champ de recherche à 22,30 px de haut :

```text
superette-el-baraka 1024x768: cible trop petite
{"largeur":487,"hauteur":22.296875,"texte":"INPUT"}
```

Les contrôles ont ensuite exposé le bouton de remise à 24,89 px et un bouton Stock à
40 px de large.

**Correction.** Les trois contrôles ont une taille tactile minimale de 42 px. Les essais
avec 187 articles de supérette et 112 articles de café ne détectent plus de cible visible
trop petite ni de débordement en 1024×768, 1366×768 et 1920×1080.

**Garde.** `catalogue-performance.browser.mjs`. Commit `0a87bcc`.

Les chiffres de navigateur sont issus d'un Chromium local et d'API simulées de façon
déterministe. Ils mesurent l'interface, pas le réseau, PostgreSQL distant, l'imprimante ou
le matériel exact d'une caisse.

| Ouverture café | 112 articles | 581 / 767 ms | 616 / 811 ms |

La médiane sous une seconde convient à la saisie courante. Le p95 d'encaissement entre

un objectif produit suffisant.

|---|---:|---:|

| Clôture journalière | 47 / 71 ms | 45 / 72 ms |

Ces traitements sont confortables sur la machine locale et ce volume. La liste de 200
clients est passée de 601 à 13 requêtes, avec les mesures détaillées au défaut 12.

## Interface et profils métier

Les parcours clavier couvrent l'ouverture d'une tuile, l'annulation, le paiement partiel,
la validation unique, Échap et les fenêtres imbriquées. Les fenêtres portent un rôle et un
libellé accessibles, et le focus reste contenu pendant leur affichage.

Les catalogues réels supérette et café ont été rendus aux trois définitions demandées. Les
contrôles programmatiques de profil couvrent les six métiers et le socle vide. Des
démarrages complets avec base réelle ont été exécutés pour café, restauration et boutique ;
prêt-à-porter, pâtisserie et parfumerie ont été vérifiés par leurs catalogues et règles de
profil, pas par six démarrages PostgreSQL séparés. La pollution « cuisine » d'une boutique
a été supprimée.

Les contrastes n'ont pas fait l'objet d'une mesure automatisée WCAG avec Axe. Les erreurs
métier principales ont été lues, mais aucun inventaire exhaustif ne prouve que chaque
message indique une action de résolution.

## Exploitation

### Sauvegarde et restauration

Une base locale contenant le mois synthétique a été sauvegardée puis restaurée dans une
nouvelle base. La source et la restauration contiennent chacune :

```text
3000 sale_order
3000 order_line
3000 payment
18 migrations Flyway (installed_rank)
```

Le fichier faisait 222 970 octets ; la sauvegarde a pris 563 ms et la restauration 669 ms.
Cela prouve la procédure locale sur PostgreSQL 17.6. Cela ne prouve ni une sauvegarde
planifiée, ni le chiffrement, la rétention ou une copie hors site.

### Migrations et panne

Les migrations Flyway V1 à V18 ont été appliquées à plusieurs bases fraîches et rejouées
au fil des suites. Leur application répétée sur un schéma à jour tient. Elles sont
orientées vers l'avant : aucun script de retour arrière n'existe. Une migration sur une
base client chargée et utilisée en parallèle n'a pas été simulée.

Les écritures de vente sont transactionnelles, mais aucun arrêt forcé de PostgreSQL au
milieu d'une vente ni remplissage du disque n'a été injecté. Il serait donc abusif de dire
que l'absence de demi-ticket est vérifiée dans ces deux pannes.

## Ce qui n'a pas pu être vérifié

- PostgreSQL 16 exactement : seule la version locale 17.6 était disponible.
- La production, son pare-feu, ses certificats, HSTS réellement servi et ses ports : tout
  accès au serveur était interdit par le périmètre.
- Une panne PostgreSQL pendant une transaction et un disque plein.
- La sauvegarde planifiée, chiffrée, hors site et sa restauration régulière.
- La réversibilité des migrations et leur impact sous charge sur les données d'un client
  actif.
- Une matrice exhaustive de chaque endpoint contre chaque rôle. Les chemins critiques
  cités sont testés, mais l'exhaustivité n'est pas démontrée.
- Un audit automatisé des dépendances contre les avis de sécurité du jour.
- Une campagne WCAG complète : contraste, zoom, lecteur d'écran et Axe.
- Le comportement sur écran tactile et imprimante physiques ; les essais ont utilisé un
  navigateur local.
- Le démarrage PostgreSQL complet des six profils : trois ont démarré réellement, les
  trois autres reposent sur les contrôles statiques et unitaires de profil.
- Le deuxième facteur du back-office éditeur, qui reste à concevoir.
- Un journal d'accès exhaustif disant qui a lu chaque donnée sensible.

## Ordre de travail recommandé

1. Remplacer les identifiants caisse connus par un secret initial unique et un changement
   obligatoire au premier accès.
2. Prototyper le résolveur de contexte client strict jusqu'à faire passer
   `TenantContextTest`, puis tester deux bases concurrentes.
3. Tester restauration, panne PostgreSQL et disque plein dans une campagne d'exploitation
   dédiée, puis automatiser une sauvegarde chiffrée hors site.
4. Mesurer l'encaissement p95 sur le matériel cible avec l'imprimante réelle.
5. Compléter la matrice d'autorisations, la revue de dépendances et l'audit WCAG.
6. Ajouter un second facteur et un journal de lecture au back-office éditeur avant son
   exposition large.
